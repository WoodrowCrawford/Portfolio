Character Vault API
A Deep Dive

An API I developed for managing character data in games.

Project Overview

Character Vault is a REST API I built in .NET (C#) for managing game character data. It's a full CRUD backend, developers can create, read, update, and delete characters, each with a name, class, and level. I built it to learn how to design a real backend API properly, so I structured it the way a production .NET service would be, rather than just throwing endpoints together.

Key Features

  • A full REST API with create, read, update, and delete operations
  • Built on the repository pattern with dependency injection, so the storage layer can be swapped out without touching the API
  • Separate request models for creating and updating, following proper API design
  • Input validation and correct HTTP status codes (201, 400, 404, 204)
  • Swagger UI for testing and documentation

Development Details

  • Framework: .NET (ASP.NET Core Minimal APIs)
  • Language: C#
  • Status: Completed
  • Platforms: Cross-platform (.NET)

What I worked on

I built this solo to teach myself how real backend APIs are designed, not just to make one that works, but to structure it the way a professional .NET project would be. What I built:

  • The full set of REST endpoints for creating, reading, updating, and deleting characters
  • A repository behind an interface, injected through dependency injection, so the data source is swappable (it currently reads and writes JSON, but nothing in the API depends on that)
  • Separate models for create and update requests, kept apart from the character entity itself
  • Validation on incoming data, with the API returning the right HTTP status code for each outcome
  • Swagger integration so the whole thing is self-documenting and testable in the browser

Development Insights

This was me stepping outside of game engines to learn proper backend development. The interesting part wasn't the CRUD itself, it was structuring the project well, using an interface and dependency injection so the storage layer isn't locked in, splitting out request models, and handling validation and status codes the right way. I learned a lot about how real APIs are designed, and it's the project that got me genuinely interested in the software side beyond just games.
